Systems

Two ways to build an operating system. Why they are the same. Why one is used anyway — and the loop at its centre.

← ICS 09 · Self-Reference II

The systems side of station III: the second incompleteness theorem as engineering. The argument is the selfie talk's Part III, compressed: two designs, the evidence that they are equivalent, the price of the faster one. Every number on this deck is selfie reporting on selfie. Book: the Computing chapter's station callouts, Emulation, Virtualization, Self-Reference.

Three problems

An operating system solves three problems. Two are ordinary. One is not.

Sharing

One processor, many programs. Give each a turn — a context switch every few milliseconds, driven by a timer. Ordinary.

Memory

One memory, many programs. Give each its own addresses and translate — paging. Ordinary, and a lot of bookkeeping.

Isolation

None of them may touch the others, or the kernel. And the kernel must be isolated from the programs whose isolation it provides. Not ordinary. This is the loop.

Self-reference is not a party trick. It is the hard part of systems, and most courses step around it because in a production kernel it is buried under a million lines. Selfie makes it the subject and keeps the system small enough that the loop stays visible.

Name the three, then point at the third. The claim to make explicitly: the circularity is what real systems are made of. Linux schedules the scheduler; a hypervisor must be isolated from the machines whose isolation it provides. It is invisible in production because it was bootstrapped once, decades ago.

Two designs

Two ways to build the same operating system.

by emulation · by virtualization

By emulation. The operating system is an interpreter. The guest's code is data being read, one instruction at a time. Isolation is free: the guest never touches the processor. No self-reference anywhere.

By virtualization. The operating system puts the guest onto the real processor and takes it back when the timer fires or the guest asks for something. The guest runs at full speed — on the same hardware as the kernel.

Selfie has both: mipster is the first, hypster the second.

Left and right. Make sure the room sees that on the left the guest is read and on the right the guest is run. That difference is everything on this deck.

In the terminal

They are semantically equivalent. Selfie can show it rather than say it.

$ make emu-emu ./selfie -c selfie.c -o selfie.m -m 3 -l selfie.m -m 2 -l selfie.m -m 1 … > selfie.m: summary: 86380 executed instructions in total ./selfie: summary: 222410917 executed instructions in total
$ make os-emu ./selfie -c selfie.c -o selfie.m -m 2 -l selfie.m -y 1 … > selfie.m: summary: 86380 executed instructions in total ./selfie: summary: 17860937 executed instructions in total

Same guest: selfie printing its synopsis. Hosted by an emulator on the left, by a hypervisor on the right. The guest executes 86,380 instructions both times — the same number, the same output. That is the evidence that the two designs are the same operating system.

Only the bill for the machine underneath differs: 222 million instructions by emulation, 18 million by virtualization. Twelve times cheaper. That is the entire reason virtualization exists.

Run both; they take a while and the numbers appear at the end. The exact numbers move with the version of selfie, so check them before class; the point is that the guest's number is identical and the host's is not. Say plainly: virtualization is needed only for performance.

For exactly one reason

What the machine underneath is billed.

instructions on the physical machine · log scale

Bare metal: 85,754. Virtualized: ×208. With a hypervisor underneath as well: ×694. Emulated: ×2,593.

And the bar chart understates the case. On real work — selfie compiling selfie — the virtualized overhead collapses to ×1.72, because the guest runs on the processor and the kernel is only involved at the edges.

That collapse is the whole economic argument for virtualization, and for the cloud.

The factor of 1.72 comes from make self-os-emu against make self-emu; quote it and say where it is measured. Emulation pays per instruction; virtualization pays per exception. That is why the ratio depends on the workload and why, on real workloads, the faster design wins by orders of magnitude.

The price

Virtualization is emulation plus self-reference.

the kernel requires what the kernel provides

The kernel provides isolation. To provide it, the kernel runs on the same processor as the guests — so the kernel needs to be isolated too. From the guests. By whom?

By itself, would be the answer, and week 8 said what that is worth. Nothing certifies itself. So real kernels do it the other way: a small piece of code, isolated by construction, that must never fault, written and checked by hand — the trusted computing base. Keeping it small is the microkernel programme.

The certification comes from outside the loop. Same shape as Thompson's second compiler. Same theorem.

This is the slide of the session, and the reason the systems side is in a class about intelligence. The kernel that needs what it provides is Gödel's second theorem in engineering clothes, and the response is the one every station of the semester recommends: an outside check, kept as small as possible. In selfie the trusted base is hypster's exception handler and context switch.

Self-hosting

A hypervisor whose virtual machines can run the hypervisor.

hypster on hypster on mipster
$ ./selfie -c selfie.c -o selfie.m -m 3 -l selfie.m -y 2 -l selfie.m -y 1 …

The third command from week 1. An emulated machine hosts a hypervisor that hosts a hypervisor that hosts selfie, which prints its synopsis. Still reasonably fast, because there is only one emulator in the stack and each hypervisor adds little.

Understand the first command and you understand compilers; the second, machines; the third, operating systems. Only the third is hard to implement, and this deck said exactly where.

Run it. Then the sentence from week 1, now earned. The systems class spends a semester making hypster do this with processes, threads and locks; here the point is that the loop closes and the machine still works.

Bounding, not deciding

The timer interrupt is the engineering answer to the halting problem.

Last week: no kernel can decide whether the program it is running will ever stop. This week: it does not try. Every few million instructions a timer takes the processor away, whether or not the program was about to finish, and gives it to the next one.

Paging does the same for space: not how much memory will it need, which is undecidable, but here is what it may have, enforced.

The pattern

What a system cannot decide, it bounds. Time by the timer, space by the page table, trust by the trusted computing base. That is Rice's theorem, answered — and it is the shape of every tool in week 12.

The sentence that connects week 9 to week 12. A bound is an approximation with a stated limit, and an operating system is a collection of them. Say that the app that stopped responding on their phone is this slide: nobody decided it was stuck, a timer bounded how long it could hold the screen.
